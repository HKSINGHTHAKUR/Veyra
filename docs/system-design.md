# System Design (Phase 5 – <800 words)

Healthcare Appointment Manager is a modular monolith. Controller → Service → Repository → PostgreSQL, with external integrations (AI, email, calendar) as isolated modules not in booking transactions. AI is isolated via `LlmClient` and `AFTER_COMMIT` events.

**Double-booking prevention** uses two layers. Application checks availability (working hours minus leave minus BOOKED/RESCHEDULED appointments minus ACTIVE non-expired holds, with slot-grid validation via `AvailabilityService.isValidSlot`). The final guard is PostgreSQL partial unique indexes: `uq_slot_hold_active (doctor_id, slot_start WHERE ACTIVE)` and `uq_appointment_active (doctor_id, appointment_start WHERE BOOKED/RESCHEDULED)`. Concurrent requests race; the loser hits a `DataIntegrityViolationException` mapped to 409. No permanent slot rows exist; slots are derived UTC Instants from `LocalDate+LocalTime`.

**Doctor leave conflicts** are checked at every booking step. A leave row (`doctor_id, leave_date` unique) makes availability empty for that date and causes hold/confirm/reschedule to return 409. Past leave creation is allowed; future leave is validated for duplicates.

**Slot hold mechanism** reserves a slot for `app.slot.hold-duration-minutes` (5 test, 10 prod). Hold creation validates the grid and that the slot is not booked or actively held (`expiresAt > now`). An expired ACTIVE hold is treated as free and expired inline before inserting the new hold, so correctness does not depend on the scheduler. Confirmation requires hold ownership, revalidation, and atomically creates a BOOKED appointment, converts hold to CONVERTED, links pre-submitted symptoms (via `slot_hold_id` → `appointment_id` after V2), and writes a notification record.

**Notification failure handling** is decoupled. Never `saveAppointment + emailService.send()` in one `@Transactional`; instead `confirm/cancel/reschedule/leave/reminder` create `PENDING` notification then commit. `NotificationProcessor` (`@Scheduled 30s`) claims work via an atomic conditional UPDATE (`claim`: `PENDING/FAILED→PROCESSING`, `attemptCount+1`, loser matches 0 rows — so duplicate sends are prevented even with concurrent workers), then sends via the `EmailService` abstraction (`SmtpEmailService` vs `FakeEmailService`), marking `SENT` or `FAILED` with `failureReason`; backoff 1/5/15 min, `max-retries 3`. `ReminderScheduler` creates 24h reminders idempotently; `DoctorLeaveService` notifies affected future appointments (past/unaffected ignored). Appointment state never depends on SMTP. The Calendar worker currently uses a simpler reload-and-check claim and assumes a single scheduler instance (documented limitation).

**Google Calendar isolation** follows the same principle: connect/callback store only minimum OAuth tokens per user (`calendar_credentials`, never exposed/logged). The browser-compatible OAuth flow uses a server-generated SINGLE-USE random state (`calendar_oauth_states`, 256-bit, 10-min TTL) bound to the initiating user — the public callback authenticates by consuming that state, never by trusting query parameters, and redirects the browser to the frontend. Confirm/reschedule/cancel enqueue DB-only `CalendarSync PENDING`; a background worker creates/updates/deletes events idempotently from DB state (no eventId→create, eventId→update, cancelled→delete) with bounded retries (single-instance worker assumption). Google outages leave appointments BOOKED/CANCELLED/moved with sync FAILED – never rolled back. All times UTC RFC-3339.

**AI failure isolation:** `AppointmentService.confirmHold` commits `BOOKED` then publishes `AppointmentConfirmedEvent`; `AiSummaryEventListener` (`AFTER_COMMIT`) calls `AiSummaryService.generatePreVisit` in a new transaction. `ConsultationService` similarly triggers post-visit. LLM timeout/exception/malformed JSON (urgency not in `LOW/MEDIUM/HIGH`, missing chief, not 3 questions, invented meds) marks `AiSummary` `FAILED` with `failureReason` (no stack), but appointment stays `BOOKED` and consultation stays `COMPLETED`. Duplicate `PRE_VISIT`/`POST_VISIT` per appointment is prevented via unique constraint.

Rescheduling validates new slot like new booking and `UPDATE`s same row (status remains `BOOKED`; `RESCHEDULED` also blocking; `rescheduledFromId` unused). `uq_appointment_active` protects new slot; on 409 original stays. Hold `GET` allows only owner patient or ADMIN (403 otherwise); cancellation allowed for owner patient/assigned doctor/ADMIN. H2 tests are best-effort; PostgreSQL `pgtest` verifies strict concurrency.
